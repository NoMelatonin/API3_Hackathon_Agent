# DisasterDAO V2

## Start und lokale Reproduktion

Node >=22.18, installierte Abhängigkeiten und Foundry wie in README. V2 erzeugt keine Schlüssel. Sie verwendet ausschließlich öffentlich bekannte, wertlose Anvil-Testaccounts. V1-Testnet-Manifeste werden nicht verändert.

```sh
npm run install:local
npm run forge -- build
npm run export-abi
npm run anvil -- --host 127.0.0.1 --timestamp 1793372440 --silent
```

In einem zweiten Terminal:

```sh
npm run v2 -- deploy --local
npm run v2 -- verify --local
npm run dev
```

Vorschau `/`, lokaler Fonds `/?local=1`, bisheriger MVP `/?legacy=1`. Beide Seiten sind eigenständige Ansichten mit getrennten ABIs und Deploymentkonfigurationen.

Deploymentdateien werden nie überschrieben. Bei einer bereits vorhandenen V2-Konfiguration diese vor einem bewusst neuen lokalen Durchlauf unter einem freien `deployments/*.local.json`-Namen archivieren; für das neue Manifest gegebenenfalls `--deployment deployments/NEW.local.json` verwenden und bei allen folgenden CLI-Befehlen denselben Pfad angeben. Nie einen laufenden fremden Anvil-Prozess zurücksetzen. Lokale Manifeste und Screenshots sind ignoriert und nicht Teil der öffentlichen Nachweise.

### Echte historische Fixtures verwenden

Originale Signaturzeiten dürfen nicht editiert werden. Die folgenden Befehle stellen **nur die historische lokale Chain-Uhr** vorwärts. Dafür muss der Fonds vorher aktiviert sein. Ist die lokale Chain bereits weiter fortgeschritten, eine frische isolierte Chain verwenden.

```sh
npm run v2 -- clock --local --campaign 0 --file fixtures/usgs-real.json
npm run v2 -- quote --local --campaign 0 --file fixtures/usgs-real.json --ngo 1
npm run v2 -- submit --local --campaign 0 --file fixtures/usgs-real.json --ngo 1
npm run v2 -- clock --local --campaign 1 --file fixtures/v2/eonet-real.json
npm run v2 -- quote --local --campaign 1 --file fixtures/v2/eonet-real.json --ngo 1
npm run v2 -- submit --local --campaign 1 --file fixtures/v2/eonet-real.json --ngo 1
npm run v2 -- emergency --local --campaign 1 --ngo 2
```

USGS zahlt exakt **1.227,347430 dUSD**, EONET **535,204081 dUSD**. UI-Anzeige auf zwei Nachkommastellen; Transfers haben sechs. Die Beispiele sind echte Signaturen mit lokalen Zahlungen, keine neuen Testnet-Nachweise. Nach dem Zeitsprung zum EONET-Abruf ist die alte USGS-Antwort erwartungsgemäß veraltet.

Neue echte Antworten nach Konfiguration der vorhandenen, ignorierten `.env`:

```sh
npm run fetch-campaign -- --campaign 1 --out fixtures/v2/NEW-eonet.json
npm run fetch-campaign -- --campaign 2 --out fixtures/v2/NEW-who.json
```

Abruf kostet laut Dokumentation 0,01 wertloses Test-aUSD. Bestehende Dateien werden vor kostenpflichtiger Arbeit abgewiesen. Die gespeicherte `data`-Zeichenfolge bleibt bytegenau erhalten. WHO wird bei einem erfolgreichen späteren Abruf **nicht automatisch aktiviert**: Datenstruktur und Filter müssen erst geprüft und anschließend ein neuer Fonds erstellt werden.

## Förderregel und Finanzierungsgrenzen

Alle Geldbeträge sind pro NGO und Einsatz. Unter der Schwelle keine Zahlung; beim Erreichen der Schwelle beginnt ein 500-dUSD-Anspruch. Danach stetiges Wachstum bis maximal 2.000 dUSD:

`P = minimum + (maximum − minimum) × (f(min(x, cap)) − f(threshold)) / (f(cap) − f(threshold))`

| Einsatz | f(x) | Schwelle | Maximum erreicht ab |
|---|---|---:|---:|
| USGS | `10^(1.5 × (x − threshold))` | 7 Magnitude | 8 Magnitude |
| EONET-Sturm | `x²` | 34 kts | 64 kts |
| WHO-Malaria | `x` | 100 Fälle / 1.000 Risikopersonen / Jahr | 300 |

Die Kurven folgen näherungsweise Erdbebenenergie, Winddruck bei gleicher Luftdichte beziehungsweise einer linearen jährlichen Inzidenz. Dies sind **Demo-Förderregeln**, keine validierten Schadens- oder Bedarfsmodelle und keine gemeinsame Schweregradskala. EONET-Windgeschwindigkeit ist kein allgemeiner Index für alle EONET-Ereignisse. WHO-Daten stellen keine akute Katastrophenwarnung dar.

Die Demo-Parameter stehen in `src/v2-config.ts`, werden beim Erstellen im Contract gespeichert und besitzen keinen administrativen Änderungspfad. Der Höchstbetrag bleibt aus Budgetgründen bei 2.000 dUSD; kleinere Schwellen, Obergrenzen und Mindestbeträge lassen sich vor einem neuen Deployment konfigurieren. Konstruktor und Mathematik prüfen sichere Parameterbereiche.

Der Contract verwendet sechs Dezimalstellen für Eingangswerte und Geldbeträge; übergenaue Eingaben werden abgewiesen, nicht still abgeschnitten. Ganzzahlfelder wie Jahr und Trefferzahl dürfen keine Nachkommastellen enthalten. Vor Exponentialberechnung beziehungsweise Quadrieren wird auf den Cap begrenzt. Solady `expWad` stammt aus dem bereits gepinnten MIT-lizenzierten Vendor-Commit in `vendor/versions.json`. Die unabhängige Referenz ist mit `python3 scripts/payout-reference.py` reproduzierbar.

Drei NGOs × drei Einsätze × 2.000 dUSD ergeben 18.000 dUSD Maximalverpflichtung. Jeder Einsatz reserviert 6.000 dUSD. Unterfinanzierte Aktivierung wird abgewiesen. Es gibt keine Verteilung nach Reihenfolge oder frei schwankendem Restpool-Anteil. Ein niedriger ausgezahlter Betrag lässt Mittel im Fonds; sie sind nicht automatisch für andere Einsätze frei. Es gibt weiterhin keinen Rückzahlungs- oder Abzugspfad.

Oracle- und 2/3-Notfallpfad teilen `claimed[campaign][ngo]`. Der Notfallpfad zahlt fest 1.000 dUSD, da kein verifizierter Messwert vorliegt. Neue Signaturen und spätere stärkere Werte erzeugen keine Nachzahlungen.

## Authentifizierte Daten und Blocker

- **USGS:** unveränderte Anfrage für `us6000jllz`; ID, Erdbebentyp, Reviewstatus, Ereignistag und Region werden geprüft. Signierte Magnitude bestimmt den Betrag.
- **EONET:** `getEvent(EONET_22386)`; Kategorie `severeStorms`, Quelle `JTWC`, Punktgeometrie, Wind `kts`, exakt 10.08.2026 06:00 UTC, Region 160–162° E / 26–29° N. Die Projektion bindet eine bestimmte Beobachtung; geänderte Reihenfolge, Einheit oder Beobachtungszeit führt zur Ablehnung. Keine Suche nach dem höchsten Wert durch den Relayer.
- **WHO:** `getIndicatorData(MALARIA_EST_INCIDENCE)` mit Nigeria, 2022 und leeren Aufschlüsselungsdimensionen. Projektion authentifiziert Trefferzahl, Datensatz-ID, Indikator, Land, Raumtyp, Jahr, Dimensionen, Inzidenz und Unsicherheitsgrenzen. Genau ein passender Datensatz ist zulässig. Sind Unsicherheitsgrenzen vorhanden, müssen sie den Punktwert einschließen. Der tatsächliche Antworttyp ist wegen des Upstream-Ausfalls noch unbestätigt; Oracle standardmäßig gesperrt. Die Gesundheitsdaten in Solidity-Tests sind ausdrücklich synthetische Testdaten, kein Integrationsnachweis.

Signer und Anfragehash werden aus Konfiguration und dokumentierter Anfrage gewählt, nie aus untrusted Antwortmetadaten. Der Contract prüft EIP-191, keine Zukunft, höchstens 300 Sekunden Signaturalter und Signatur nach Aktivierung. Historische Beobachtungszeit und Signaturzeit bleiben getrennt. Doppelte JSON-Schlüssel einschließlich escaped Varianten werden zurückgewiesen.

Quelle, Request und der konkrete WHO-Fehler stehen in `docs/sources/STATUS.md`; OpenAPI-Snapshots liegen daneben. Die echte EONET-Fixture hat SHA-256 `aa758b39b4ab0044bd2e8a5c5a05e7fc18dad7ba26b16be7bc221e12f08203b8`.

Mathematische Grundlagen: [USGS magnitude and energy](https://www.usgs.gov/programs/earthquake-hazards/earthquake-magnitude-energy-release-and-shaking-intensity), [NASA dynamic pressure](https://www1.grc.nasa.gov/beginners-guide-to-aeronautics/dynamic-pressure/), [WHO indicator definition](https://www.who.int/data/gho/data/indicators/indicator-details/gho/malaria-incidence-%28per-1-000-population-at-risk%29).

## Verifikation

```sh
npm run typecheck
npm test
npm run forge -- test
npm run check-real
npm run build
npm run test:ui -- e2e/v2.spec.ts
```

Browserprüfungen benötigen eine frische lokale Chain und ein vor den Fixtures aktiviertes V2-Deployment. Sie stellen ihren Chainzustand nach jedem Test wieder her. Für alle V1- und V2-Browsertests zusätzlich den unveränderten V1-Fonds auf derselben frischen Chain deployen (`npm run deploy -- --local --deployment deployments/NEW-v1.local.json`, vorhandene V1-Testrollen erforderlich), dann `npm run test:ui`.

Geprüft am 30.10.2026: 23 TypeScript-Tests, 50 Solidity-Tests einschließlich 1.000 Fuzz-Durchläufen je Fuzz-Test, 14 Browserprüfungen inklusive fünf erhaltener V1-Regressionen; Produktionsbuild und lokale Runtime-Verifikation. Die Erdbebenkurve besteht 1.001 unabhängige Decimal-Referenzpunkte mit maximal einer Mikro-dUSD Abweichung. Dies ist keine formale Verifikation des gesamten Contracts.

Browserchecks belegen lokale echte Zahlungen für USGS und EONET, abgewiesene Manipulationen, fehlende Wallet/RPC, unverbindlichen Slider, Anspruchssperren, Quorumtrennung und Layout ohne horizontalen Überlauf bei 375/768/1.440 px. Desktop und Mobil wurden visuell geprüft. Kein Video wurde erstellt. Öffentliche V2-Deployments oder Auszahlungen wurden nicht vorgenommen.

## Demo-Theme

V2 und lokale V2 laden `web/demo-theme.css`; Komponentenfarben kommen aus Tokens in `web/style.css`. Dark Mode ist neutral schwarz/grau mit hellen Aktionen und violettem Fokus/Diagramm. Light Mode behält grüne Akzente. Theme-Auswahl (`v3-theme`) ist mit V3 geteilt. V1 lädt weiterhin das bisherige Legacy-Theme.
